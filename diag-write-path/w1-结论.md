## 2. 最强的一条证据：键盘真的在推动游戏

把 `[KEYRECV]` / `[CLICK]` / 步骤完成 / `[STATE]` 按发生顺序对齐（`tools/log-events.mjs` + 一次性对齐脚本）：

```
key   shake <- Y
--- 一步完成
key   shake <- Y
--- 一步完成
t= 43 work=[shake:#5 mash:5/6 fire:- chem:- brew:-]
key   shake <- Y
--- 一步完成
```

**按键 56 次**（`shake×27  fire×7  brew×11  pack×8  chem×3`），**鼠标只有 5 次命中**，
而**步骤完成 39 次** ⇒ 推进主要来自键盘。**"键盘没反应"在本轮没有复现。**

另外两条顺带验证：

- **光标 y 轴口径是对的**：`[CLICK] raw=(629.17,455.00) canvas=(-170.83,5.00) hit=chem`
  —— 点中间那排命中中间那排（就是 `教训` §9 用负对照修掉的那个镜像 bug）。
- 菜单点击开局、`pack` 键出餐都走到了（`pack×8`）。

## 3. 顺带抓到的一个真 bug（无害，但每帧报错 5231 次）

```
[WERR] tag=host.setColor ctrl=Pk_hint val=176 err=xuehuang:1452: cannot set imageColor, no such field
...
[WERR-SUM] kinds=1 hits=5231 | host.setColor@Pk_hint x5231
```

`Pk_hint` 是**文本框**，而 `imageColor` 只属于图片控件 ⇒ 每帧写、每帧失败。

**为什么不冻画面**：`H.setColor` **没有缓存**，失败了下一帧照样重写 —— 没有"记成已写过"，
所以落不进 §A 那个陷阱。（这正是"缓存 + 失败"必须成对出现才致命的最好例证。）

**顺带发现**：真机报错**自带脚本名+行号**（`xuehuang:1452:`）——
以后定位真机报错可以直接跳到行号，不用猜。

## 4. 本地复现出来的"缓存投毒"在真机上**没有**出现（重要）

本地 `probe-bundle` 里 `view.setText` 打在 `HudTip` 上失败并打出 `[WERR-CACHE]`，
根因是 `view.lua:736` 的 `st.name:sub(1, 2)` —— `string.sub` 按**字节**切中文，切出半个汉字。

**真机日志里 `cannot convert invalid utf8` 出现 0 次** ⇒ 平台不校验这个，
写入没失败、也就没有投毒。

⇒ 它仍然是**要修的显示 bug**（HUD 提示行会带半个汉字），但**不是**"按键没反应"的病因。
正确写法参考同文件 `clip()`：**按字符宽度推进**，不按字节切。

## 5. 为什么**没有**做 `forceWrite=1` 对照轮

`forceWrite=1` 的设计目的是切开"病在缓存"还是"病在写入本身"。
现在 `[WERR-CACHE]` = 0、画面正常 ⇒ **两条分支都已经被排除**，对照轮不再提供新信息，
而代价是又一次脚本变量改动 + 重新导入 + 保存关卡 + 进关卡。
（要跑也能跑，见交接 §5.5；只是预期不会有新结论。）

## 6. 诚实列出"本轮没能确定"的部分

1. **是哪一处改动让键盘变好的，本轮没有对照。**
   真机日志只证明"当前源码可用"⇒ 不证明"哪一处让它可用"。
   源码里最可疑的一处是入口的 `IN.forceQueue = true`（键盘回调只登记、由 `OnUpdate` 帧内消费）。
   要做一刀切开的 A/B 很简单：把它改回 `false` → 重新导入保存 → 按键看还灵不灵。
   ⚠️ 注意：模拟器作者的真机探针显示两类回调**时机相同**（`inUpdate=false`），
   所以"帧外不重绘"这个机制**并未被本轮证实**；本轮只证实了"当前源码能用"。
2. 真机画布 1600×900、`panel=nil`、容器 0×0 兜底 —— 记录在案，未深挖。
3. 本轮的观测点只覆盖**写入路径**，不覆盖音频/手柄/移动端。
