# 为什么"坏的那版在模拟器上似乎就好、真机就坏"？

> 2026-10-01 晚补查。起因：用户直接指出"问题的重点不应该是为何那一版坏的在模拟器上似乎就好，实机就坏呢"。
> 证据：真机上坏的那份产物 `dist/diag-w1-backup/20261001-232656/xuehuang.lua.before`（128415 B，关卡里嵌的就是它）
> 在**本地模拟器**里被我重新跑了一遍；配合官方类型注解 `lua/types/mihoyo_client_ui_api.d.lua`。

---

## 0. 结论（先给答案）

**它不是"在模拟器上就好"。** 我把真机上坏的那份产物（d2 代）拿进模拟器量，它**同样不响应工位键**；
而且原因不是平台语义，是**纯逻辑口径**：

> **d2 的工位卡印的键（`B` / `C`）和它真正绑定的键（默认物理键 `1` / `K`）根本不是一回事。**

"本地看着好、真机坏"这个表象 = **判据不看这件事** + **一台永远打 ✓ 的坏仪表**。
⇒ 平台侧没有任何未建模的语义需要为这件事负责。

---

## 1. 三份互相独立的证据

| 证据 | 内容 |
|---|---|
| **d2 产物自己的启动日志** | `[input] 已绑定：shake=KeyboardCraftspersonKey1Down  fire=Key15Down  chem=Key20Down  brew=Key18Down` |
| **d2 产物自己的界面代码** | `{ id='shake', name='捣锤区', key='B' }`、`{ id='chem', name='化学区', key='C' }` —— 卡片印的是**硬编码的原版字母** |
| **官方类型注解** | `KeyboardCraftspersonKey1Down # 键鼠：奇匠按键1（默认物理键：**1**）`；`Key20Down  # 默认物理键：**K**` |

d2 产物里甚至留着一行正确的注释草图，说明当时已经发现过：

```
--    捣锤区 1   火系区 H   化学区 K   萃茶区 P    打包台 空格
```

—— 但卡片那一行还是 `key = 'B'`（界面与实际各写各的）。

## 2. 于是"玩家按屏幕告诉他的键"会发生什么

| 工位 | 界面印的 | 实际绑的 | 默认物理键 | 按界面上的键 |
|---|---|---|---|---|
| 捣锤区 | **B** | `Key1` | **1** | ❌ 什么都不发生 |
| 火系区 | H | `Key15` | H | ✅ |
| 化学区 | **C** | `Key20` | **K** | ❌ 什么都不发生（得按 K 才行） |
| 萃茶区 | P | `Key18` | P | ✅ |
| 打包台 | 空格 | `KeyboardJumpKey` | 空格 | ✅ |

四个工位里**两个"印的键按下去没有任何事发生"**；而用户嘴里的 `yhpk` 里 `Y` 更惨——
d2 **压根没绑** `Key13`（它绑的是 `Key1`）。

> ⚠️ 这也解释了外部顾问 09-27 的复现输出为什么是"**部分键有反应**"：
> `Y ✓ / H ✓ / P 有活却状态不变` —— "某个全局条件"（帧内帧外、重绘）解释不了"只哑几个"，
> 但"**每个工位各绑各的键、界面又各印各的**"天生就是"有的灵有的不灵"。

## 3. 原症状的机械原因：鼠标为什么一定有用

d2 产物里的点击路径：

```lua
if IN.hit(v, slot.box, 8) then IN.clearClick(); return G.act(st.id, 'press') end
```

**鼠标是命中测试之后直接调 `G.act` —— 整条路根本不经过键位映射**；
而键盘必须先命中一个**已绑定**的枚举键，才轮得到 `G.act`。

⇒ "鼠标点它正常、键盘按它没反应"是这两条路的结构性差异造成的，
与"帧内/帧外""写控件重不重绘"**没有任何关系**。
（作者当年的真机探针说"两类回调时机相同、按键行 9 项全正常"——**他也对**：键回调本身没问题，
问题在我们**把哪些键绑上了、又在界面上印了哪些键**。）

## 4. 为什么当年本地"看着好"（这才是要回答的那半）

1. **判据缺口**：当年没有任何一条断言在检查"**界面印的键 == 实际绑的键**"，
   也没有检查"**按下去必须有回应**"。这两条是后来才写进 `tools/ui-oracle.mjs` 与 `lua/test/e2e_key_test.lua` 的
   （`docs/tech-architecture.md` 里"**同一个问题只能有一个判据函数**"那段就是为这个缺口写的）。
2. **坏仪表**：`tools/key-check2.mjs` 在状态**没变**时照样打 ✓（外部顾问发现）。
   他 09-27 那份本地输出里 `P(brew) ... → 一模一样` **就是病征本身**，只是被那句 ✓ 读成了"通过"。
   ⇒ **模拟器从来没说它好，是我们的仪器说了它好。**
3. **d2 还有第二个哑区：入场方式**。d2 是"**按空格开始**"，没有「开门营业」按钮：

   ```
   [雪皇] 已就绪 BUILD=xuehuang-d2 —— 按空格开始
   ```

   没按空格就停在菜单里 —— 那一状态下**按什么都不会有反应**（鼠标也只有一个开场入口）。
   现在的版本是"菜单 + 点屏幕开门营业／确认键"，且真机日志里能看到 `[key] click 754 536` 这一步。

## 5. 现在这份为什么在真机上是好的（逐条对得上）

| 现在的做法 | d2 有吗 | 作用 |
|---|---|---|
| 显式 `IN.BIND` 键位表 | ❌ | 绑定就是 Y/H/K/P/空格，不再靠"逐键枚举"撞运气 |
| 界面键位**从 `IN.primary` 读**（`view.lua` 的 `keyOf`） | ❌ | **印的键永远等于真按得响的键** |
| `opt.route`（票不在本工位就自动送过来再动手） | ❌ | **按下去一定有回应** |
| `stationState`（工位卡/小票卡/HUD 同一判据） | ❌ | 界面不再自相矛盾（"小票说按 P、工位卡说按 P 无效"） |

真机日志两边对上了：`press=[shake=Y fire=H chem=K brew=P pack=SPACE]` + 56 条 `[KEYRECV]`
（`shake×27 fire×7 brew×11 pack×8 chem×3`）→ 39 次步骤推进。

## 6. 仍然没对照的一件事（别把它当已解决）

`IN.forceQueue = true`（键盘回调只登记、由 `OnUpdate` 帧内消费）——**d2 没有它，现在这份有**。
所以"帧外写控件不重绘"到底是不是真机制，**本轮仍然没有对照**。
它值得一次真机 A/B：当前源码 + `forceQueue = false`，看画面会不会又死。

⚠️ 如果那一刀下去画面真的死了，就等于在真机上补上了作者探针**覆盖不到**的场景 ——
他的探针没测"**运行时实例化出来的控件 + 写字号/字色**"，而我们的界面**整个**都是用
`game.InstantiateClientUIControl` 现建的、并且大量写 `fontSize`/`fontColor`（`教训` §9.4 他自己列过这个未测项）。
