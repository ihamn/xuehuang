# diag-write-path —— 「真机画面不更新」写入链路诊断（交接给电脑用）

**这个文件夹是干什么的**：一次真机部署，把"按了键/点了鼠标，逻辑在走、画面不动"的病因切开。
**不需要你懂代码**：文件夹里的东西是给电脑上的 AI 或你自己照做的。

| 文件 | 用途 |
|---|---|
| `给电脑上的AI-交接.md` | **长文本**：把整件事（背景、已排除的、三个假设、要做什么、怎么判定）一次说清，直接粘给电脑上的 AI |
| `写入点清单.md` | 逐字的改动清单（改哪个文件、哪一行、原来是什么、改成什么）——**已逐条核对过原文存在** |
| `diag.lua` | 诊断模块，复制成 `lua/src/diag.lua` 即用（已用真编译器验过语法） |

## 三句话背景

1. 真机上：同一个操作，**鼠标点正常、键盘按没反应**；日志里动作是成功的（`ok=true`），画面不动。
2. 我们原先猜是"键盘回调跑在帧外、写控件不重绘"——**已被模拟器作者的真机探针证伪**
   （两行相同控件、两种触发方式、9 种写入，按键行全部正常）。作者指出的真正嫌疑是：
   **某次写入在真机上报错、被 `pcall` 吞掉，而控件缓存已经记成"写过了"** ⇒ 之后永不重写。
3. 所以现在要做的事只有一件：**让每一次写入都把错误说出来**，再上真机跑一次。

## 判定表（拿到日志后照这个看）

| 日志里看到 | 结论 | 下一步 |
|---|---|---|
| `[WERR] ... err=integer expected` | 字号写了非整数（作者给过的真机报错） | 取整后再写（`view.setStyle` 是唯一没护栏的字号写入点） |
| `[WERR-CACHE] ...` | **确诊**：某次写入失败后，缓存把"没写成功"当成"已显示" | 修法：写入失败时**不要**更新缓存（或失败后强制下次重写） |
| 只有 `[WERR]` 没有 `[WERR-CACHE]` | 有写入在失败，但还没卡住画面 | 先把那个 `tag`/`ctrl` 的错误修掉 |
| `[BOOT] bootErr=...` | 启动就抛错，`OnUpdate` 每帧提前 return | 修启动错误（这是"按什么都没反应"的另一个入口） |
| `[SYNC] afterAct err=...` | 刷新函数本身在报错（以前被静默吞掉） | 按错误修 `V.sync` |
| **一条错误都没有，画面仍不动** | 真机确有我们还没发现的规则 | 把**原样日志**+产物发给作者，请他做逐帧比对 |

`forceWrite=1`（脚本变量）是判定的关键一刀：**每帧无视缓存强制写**。
- 画面恢复了 ⇒ 病在缓存/写入失败（上表第 1~3 行）；
- 画面依旧不动 ⇒ 病在写入本身或目标控件（最后一行）。

## 做完要回退

诊断是**观测代码**，不是修复。确认病因后：
删掉 `lua/src/diag.lua`，把 `写入点清单.md` 里的改动逐条还原（或 `git checkout` 那三个文件）。
