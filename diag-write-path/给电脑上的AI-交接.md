## 0. 一句话任务

给「控件属性写入」加上**错误可见性**，然后上真机跑**一次**，把下面三个假设切开：

- **A**（主嫌疑）：某次写入在**真机上报错**、被 `pcall` 吞掉；而 view 层的缓存**已经记成"写过了"**
  ⇒ 之后每帧都判定"值没变"、直接 return ⇒ **画面永久停在那一帧**。
- **B**：缓存逻辑本身有问题（值根本没写成功却被当成已显示）。
- **C**：启动阶段就抛错（`bootErr`）⇒ `OnUpdate` 每帧提前 `return`，逻辑靠键回调照跑（日志正常、画面全死）。

**不要**去"顺手修 bug"。这一步只做观测，结论出来再改。

## 2. 症状（真机实测，照抄，不要改写）

1. **同一个操作，鼠标点它正常、键盘按它没反应**（进度会涨、字会变 vs 什么都不动）。
2. 日志里动作是**成功**的（`[LOGIC] ... ok=true`），逻辑在推进，**画面不动**。
3. 不是所有键一起哑的简单情况：外部顾问当年的复现输出是
   `Y(shake) ✓ 状态变了`、`H(fire) ✓ 状态变了`、而 **`P(brew)` 有活却状态不变**。
   ⇒ **"某个全局条件（比如回调上下文）"解释不了"只哑一个工位"**；
   "某个控件的某次写入失败"才解释得通。
4. 后来用户口径变成"不管什么键都坏"——**可能叠加了 C（启动报错）**，也可能是另一次构建的现象。
   两种都要在日志里找证据，不要先入为主。

## 4. 作者给的排查方向（原样保留）

1. 有没有某个分支**跳过了实际写入**，或者**写入时报错被吞**，但缓存照样记成了新值；
2. 按键分支和点击分支**是否调用同一个刷新函数**，按键那条路径有没有漏调或提前 `return`；
3. 按键回调里有没有**创建实例、调整层级、销毁控件**，写入的对象是不是**后来被替换掉的那个控件**。
4. 一个排查技巧：**在 OnUpdate 里每帧无视缓存强制写一遍**。如果画面恢复 ⇒ 病在缓存逻辑。
5. 已知的真机报错例子：**字号写成小数**时真机报 `integer expected (P28)`。

## 5. 这次具体怎么做

### 5.1 放诊断模块
把 `diag-write-path/diag.lua` 复制成 `lua/src/diag.lua`。

### 5.2 按清单改写入点
照 `diag-write-path/写入点清单.md` 逐条改（**逐字的原文→改后**，已核对过原文存在）。
核心思路：把每个 `pcall(function() c.X = ... end)` 换成 `D.try('标签', c, 值, function() ... end)`，
并把"缓存命中就 return"改成"缓存命中时，如果这个控件上次写失败过，就打一行 `[WERR-CACHE]`"。

> 清单里打 ★ 的必须改（每帧都走、最可能冻结画面）；○ 的是建控件阶段，可选但推荐。
> **注意**：`host.lua` 里有两行一模一样的 `pcall(function() c.fontSize = size end)`
> （分别在 `H.setFont` 和 `H.fitText`），**别用全局替换**，按函数逐个改。

### 5.3 本地自检（在电脑上也能跑，不需要游戏）

```bash
node tools/lua-compile.mjs                            # 必须 0 错
node tools/lua-test.mjs lua/test/kitchen_test.lua     # 诊断只加观测，逻辑测试应照旧全过
node tools/lua-test.mjs --entry=xuehuang --out=dist/xuehuang.diag.lua
node tools/bundle-lint.mjs dist/xuehuang.diag.lua     # 上真机前必过：非 ASCII 必须全部转义
```

⚠️ 产物名请用 `dist/xuehuang.diag.lua`，**不要覆盖**线上的 `dist/xuehuang.lua`。
⚠️ 打包器自动收录整个 `lua/src`，新增 `diag.lua` 会让"模块数"哨兵断言 +1 —— **断言红了是对的**，
   在断言旁边写一句"多了 diag.lua（诊断用）"即可，别删断言。

### 5.4 上真机（三步，缺一不可）
1. 编辑器里**重新导入脚本**：`dist/xuehuang.diag.lua`；
2. **保存关卡**；
3. 进游戏，做这几件事（按顺序，每步之间停 3~5 秒，方便在日志里分段）：
   - 等菜单出来 → 点"开门营业"进游戏；
   - 用**鼠标**点一个有活的工位，确认进度正常；
   - 用**键盘**按同一个工位对应的键（Y/H/K/P）；
   - 再按几次别的键；
   - 如果画面一直不动，停在那里 15 秒（让 `[WERR-SUM]` 打够几行），然后退出。

### 5.5 再跑一次"强制写"对照（关键一刀）
在编辑器里给脚本加变量 **`forceWrite=1`**，重新导入 + 保存关卡 + 进游戏，重复 5.4 的按键。

| 这一轮 | 说明 |
|---|---|
| 画面**恢复** | 病在缓存/写入失败（假设 A/B） |
| 画面**依旧不动** | 病在写入本身或目标控件 ⇒ 真机确有我们没发现的规则 |

### 5.6 收日志
取 `Beyond_Debug_Log` 里**最新那个 `.gia`**，原样保存（**不要截断、不要只挑几行**）。
日志里要捞的关键字（全 ASCII）：`[DIAG]`、`[WERR]`、`[WERR-CACHE]`、`[WERR-SUM]`、`[BOOT]`、`[SYNC]`、
以及现有的 `[DISPATCH]`、`[STATE]`、`V.sync`。

## 6. 判定表（拿到日志后照这个下结论）

| 日志现象 | 结论 | 下一步 |
|---|---|---|
| `[BOOT] bootErr=...` | 假设 C 成立：启动抛错、每帧 return | 按错误原文修启动路径 |
| `[SYNC] afterAct err=...` | 刷新函数在报错（以前被静默吞掉） | 按错误修 `V.sync` |
| `[WERR] ... err=integer expected` | 字号写了非整数 | 取整；`view.setStyle` 是唯一没护栏的字号写入点 |
| `[WERR-CACHE] ...` | **确诊 A**：写入失败后缓存把"没写成功"当成了"已显示" | 修法：写入失败时不要更新缓存 / 失败后强制下帧重写 |
| 只有 `[WERR]`，无 `[WERR-CACHE]`，且画面也不动 | 写入确实在失败，但还没闭环 | 先修那个 `tag`/`ctrl` 的报错 |
| **一条错误都没有 + 画面仍不动 + `forceWrite=1` 也无效** | "真机确有未知规则" | 把原样日志 + 产物 + 现象发给作者做逐帧比对 |
| `[DIAG] on=true forceWrite=false` 都没出现 | 诊断没进包/没生效 | 回 5.2、5.3 检查（脚本变量拿的是编辑器里定义的值） |

## 7. 纪律（避免又绕远路）

1. **一次只改一个变量**：这一轮只加观测 + `forceWrite` 开关，**不要顺手改玩法/表现逻辑**。
2. **别把"帧外不重绘"写进模拟器**：作者明确反对（会让正确代码在本地变红 = 伪造真机行为）。
3. **本地绿 ≠ 修好**：这个 bug 本地看不见，判据只有真机日志。
4. **别改 KEYMAP**、别信 `tools/key-check2.mjs` 的 ✓（它在"什么都没变"时也报成功，是坏仪表）。
5. **别覆盖线上产物**（`dist/xuehuang.lua`），诊断用 `.diag` 后缀。
6. **诊断做完要回退**：删 `lua/src/diag.lua` + 还原清单里的改动，别把观测代码留在正式版里。
7. `input.lua` 近期有人在改绑定（可能有未提交改动），**别动它** —— 本次诊断不需要改它。
