# 对外反馈稿：帧外写控件属性 → 真机不重绘

> 用途：把这个"只有真机能复现"的结论反馈给模拟器作者 / 社区。
> 事实来源：`还原度重做-r1-交接.md`、`按键无反应-复现结论（外部顾问）.md`、

## 一、给仓库作者（GitHub issue，推荐）

仓库：`1475505/miliastra-beyond-simulator`（issues 开着，当前 0 个）
标题建议：**把"帧外写控件属性不重绘"做成可选的模拟语义 + lint（可提供真实负对照）**

正文：

```
## 背景：一个只有真机能复现、本机全绿的问题

在一个真实项目（客户端 Lua + 客户端控件，约 60 个控件池）里遇到过：

- **键盘按键回调**里写控件属性（`c.text` / `c.fontSize` / `c.imageColor` …）→ 真机上**不重绘**，
  屏幕上纹丝不动，但逻辑正常推进、日志正常；
- **同一个动作改用鼠标点击**（光标事件）→ 立刻正常显示、进度正常走；
- 真机日志里按键事件、动作执行（ok=true）全都有，**看日志完全查不出来**。

我们最后定位到：键回调是引擎在两次 `OnUpdate` 之间调进来的（帧外/输入上下文），
在那个上下文里写属性真机不落屏；配合"值没变就不写"的控件缓存（`if cache[c]==s then return end`），
就变成**永久不刷新**——下一帧帧内同步认为"值已经写过了"，于是引擎再没机会在帧内写一次。

## 为什么这跟模拟器有关

在我们的模拟器回归里，`rt.injectKey(...)` 之后写属性**立刻生效**——键回调与点击回调
在模拟器看来**完全等价**。于是这类"上下文错了"的 bug 在本机永远测不出来：
我们 131 条断言 + 全按键路径的端到端整局用例**全绿**，真机依旧全坏。

## 建议（都不破坏现有行为）

1. **可选语义**（默认关）：`frameContext: 'strict'` —— 只有 `step()` 期间发生的控件属性写入
   进入"可见渲染状态"；帧外写入只改数据、不落屏；
2. **出一个 lint/报告**：某一帧内如果出现"帧外写过、但帧内没有再次写达该值"，
   就报"真机不刷新风险"——这正是真机不刷新的判据；
3. 可选：`script:isInFrame()` 之类的自证接口（我们临时用 `IN.inFrame` 在 OnUpdate 入口置位，
   能用但属于应用层 hack）。

## 我们可以提供的负对照

同一项目的 8 个真机部署版本里，"坏"与"修好"两版都在：
- 坏版（键回调直呼、无 `forceQueue`）→ 期望 lint **红**；
- 好版（把动作登记、由 `OnUpdate` 里的 pump 在帧内处理）→ 期望 lint **绿**。

如果你们愿意加这个模式，我可以把这两个版本整理成最小 fixture 提 PR。

## 一点不确定

不确定这属于引擎的既有行为，还是我们误用了 API。如果是后者，
也希望能把"写控件属性必须在帧内（OnUpdate）"这条约束写进文档或类型注解——
它对社区是**隐形**的：日志全对，屏幕上什么都不动。
```
