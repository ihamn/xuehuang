二、真机结果：你给的三个嫌疑，一个都没发生
  - [BOOT] ok        → 没有启动报错（"启动抛错让 OnUpdate 每帧 return"排除）

    **写入失败**必须和**缓存记成已写**成对出现才致命；只有失败、没有缓存，是不会卡的。

真因是——脚本是**保存进关卡存档**的，我们关卡里嵌的那份比源码**旧了 5 天**，
一直以为在测新版，实际跑的是旧版（改文件 ≠ 生效，必须重新导入 + 保存关卡）。
这一轮是当前源码第一次真正送上真机。
所以上次那条"真机上有报错被吞掉"的路，我们这次**证据不足**；"修复没送到现场"才是主因。

    —— 我们本地就是靠这个抓到了那个显示 bug，很有用；
  - 真机：**完全没事**，一次都没报，只是那一行显示上缺半个字。
⇒ 也就是说会出现"本地红、真机没事"。要不要记进已知差异由你定，
 我们只是觉得这条对"拿模拟器当回归"的人有用（方向跟平时相反，平时是本地绿、真机红）。

## 三、GitHub issue 版（可选，仅当你想提 issue / PR 时用）

标题：**一条真机负对照：`pcall` 吞掉的写入失败 + "先记缓存再写入" 必须成对出现才会冻画面**

```
背景：客户端 Lua + 客户端控件池，真机上曾出现"按键没反应、逻辑在走"。
按 issue 里的讨论，我们把每个控件写入点的 pcall 返回值都检查了（失败打 [WERR]），
并加了一条判据：缓存命中 + 该控件上次写失败过 → 打 [WERR-CACHE]。上真机跑了一轮。

真机结果：
- 启动无报错；帧内同步无报错；[WERR-CACHE] 0 次；
- 唯一每帧在报的是"给文本框写 imageColor → cannot set imageColor, no such field"，
  而该写入点没有缓存，失败数千次也没有冻住画面。

⇒ 可供参考的两条经验：
1. "写入失败被 pcall 吞掉"本身不会卡住画面；**只有叠加"先记缓存再写入"**才会变成永久不刷新。
   这条机制的判据可以做成一个可选的 lint（值没写成功却记成已显示 → 报风险）。
2. 模拟器在字符串合法性上比真机**严**：含非法 UTF-8 的字符串写入 text，
   本地 Fengari 抛 `cannot convert invalid utf8 to javascript string`，真机不报错。
   会不会需要进"已知差异"，由你们定。

我们这边不需要任何改动，只是把这条负对照留个记录（之前那份"帧外写不重绘"的结论已作废）。
```
