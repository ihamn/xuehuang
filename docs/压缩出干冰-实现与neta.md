## 一、先看清"恶搞"落在哪（这一步定了，实现才不会跑偏）

配方原文两步：**「快速压缩内部空气至 25000 千帕」→「继续压缩，直至出现固态干冰」**。

| 梗源 | 怎么好笑 |
|---|---|
| **24999 千帕的空气里根本没有二氧化碳** | 干冰 = 固态 CO₂。空气里 CO₂ 只占 0.04% ⇒ **压到 25000 千帕也压不出干冰**。这是配方原有的科学胡闹，也是最硬的一层 |
| **25000 千帕 = 250 bar ≈ 250 个大气压** | 数字"看着很科学"：CO₂ 在常温下约 7.4 MPa 就临界了，25 MPa 属于**超临界**——它连"干冰"都不是，是**超临界流体**。数字选得很刁 |
| **徒手把一杯柠檬水压到 250 bar** | 你用的工具是**柠檬锤**（捣果肉的），而杯子连形变都没有——"这杯子什么材质" |
| **干冰的现实身份** | 酒吧/演唱会的**喷雾道具**。一杯饮料的工序，最后做出来的是**演出耗材** |

## 二、实现方案（能落到千星图元上）

### 表现总表（控件预算 ≈ 10）

| 件 | 图元 | 数 | 什么时候出现 |
|---|---|---|---|
| 气泡 | 圆（100002） | 4 | 第一阶段满 6 下之后 |
| 液面结霜白边 | 方块 | 1 | 第二阶段满 6 下 |
| 液体上白雾层 | 方块（半透明白） | 1 | 同上 |
| 杯口白雾（**层叠**假装渐变） | 方块 | 3 | 同上 |
| 压力读数（复用 HUD 的文本框） | 文本 | 0~1 | 全程 |

> 千星没有渐变 ⇒ 白雾用 **3 层方块、由下往上宽度与透明度递减**来假装。
> 全部平时 `setSize(0,0)` 隐藏 ⇒ 不占画面，只占预算。**一杯 ~10 个控件**，三角+遮挡方案下完全放得开。

### 阶段 A：先压 6 下（"至 25000 千帕"）

| 每次下锤 | 表现 |
|---|---|
| 杯身 | 三角宽度按累计量**收窄**（−2% × 次数）——"被压扁" |
| 液面 | 每下**降 1%**（体积被压小，物理上说得通） |
| 杯身抖动 | 幅度随进度加大（用**我们自己的 LCG**，`math.random` 被禁） |
| 读数 | `压力 4120 / 25000 千帕` —— **数字是非线性的**：`p = 25000 × (i/6)^1.6`，越往后涨得越猛（手感上"越来越费劲"）|
| 满 6 下 | **气泡**出现（4 个圆，在下部随机上浮）|

### 阶段 B：再压 6 下（"直至出现固态干冰"）

| 每次下锤 | 表现 |
|---|---|
| 杯身 | 收窄继续累积（−2% → −8%）——比阶段 A 更明显 |
| 液面 | 继续微降 + 液面线**抖动加剧** |
| 满 6 下 | ① **闪白一帧**（"顶到极限"的那一下）② 液面一圈**结霜白边** ③ 液体覆一层浅白 ④ 杯口上方 **3 层白雾**并缓慢上飘 |

### 四条手感规则（真正的成败在这）

1. **进度必须看得见**：靠**压力数字 + 杯身形变**，不能只靠动效（动效会被"手在忙"忽略掉）
2. **不许一下跳完**：6 下均分（已定）
3. **"顶到极限"那一下要有标志事件**：抖动最大 + 闪白 + 霜边同时出现
4. **恶搞要落在文案上**：数字、霜、雾都好做，好笑的是"这也能叫干冰"——所以**完成时该有一句台词**

## 六、物理一致性：刚性锤头**封不住**（用户 2026-10-01 的观察 + 定量）

**用户的观察**：柠檬锤的横杆**不能伸缩**，而杯壁**有斜度** ⇒ 气体从缝里逸散。这是搞笑效果吗？

**算一下**（内壁宽：杯口 94.0 / 液面 70% 处 84.8 / 杯底 63.2）：

| 锤头宽 | 杯口缝 | 液面70%处缝 | 杯底缝 | 能"正好贴住"的高度 |
|---|---|---|---|---|
| **62**（现方案） | 16.0px | 11.4px | 0.6px | **−3.9%** ⇒ 在杯底以下，**永远贴不住** |
| 84（= 液面处内壁宽） | 5.0px | 0.4px | −10.4px | 67.5% ⇒ 从杯口**一路漏着**下 64px 才封住，再往下杯子比锤头窄 ⇒ **卡死** |

⇒ **刚性锤头在这只杯子里压不出任何压力**。这不是"要不要做成笑点"的选择题，
不解决就**压根没有"压缩"这回事**（气体全程从缝里跑掉）。

### 三条出路

| 方案 | 物理上成不成立 | 代价 | 备注 |
|---|---|---|---|
| **A. 认了，当笑点** | ✗（靠纯胡闹撑） | 0 | 代价：**25000 千帕那句很讲究的数字白写了** |
| **B. 锤头改锥面配合**（与杯壁同斜率 4.45°）| ✓（玻璃磨口塞/软木塞原理）| 锤头 1 方块 → 三角+遮挡 **2 个**（共 3）| 硬对硬仍会卡；外观更像研磨杵 |
| **C. 锤头改软质（就是一颗柠檬）** | ✓（软材料变形贴住锥面）| **仍是 1 个方块** | 一压出汁，**汁与果肉把缝糊住** ⇒ 物理与主题双对 |

**推荐 C + 把"第一下漏气"做成笑点**：

> 第一下：气压几乎不涨 + 台词「漏气了。柠檬：我来。」
> 第二下起：柠檬压软、封住 ⇒ 气压开始涨。
>
> 顺带解释了**为什么气压曲线是非线性的**（`25000×(i/6)^1.6`：前面在漏，后面才真压）。

### 顺便挖出来的两层

1. **免费 gag**：真封住之后，250 bar 在薄玻璃杯里 ⇒ **杯子应该炸**。
   所以「继续压缩，直至出现固态干冰」其实是**"在杯子炸之前把 CO₂ 压成固态"的竞速**
   —— 之前悬着的"要不要做超压失败"，现在有物理依据了（不必硬加失败态）。
2. **修正本文第二节的一处物理错误**：原文写"液面每下**降** 1%（体积被压小）"——错。
   液体不可压缩，锤头插进去**挤占体积 ⇒ 液面上升**。
   ⇒ 正确写法：**液面随行程上升**，被压下去的是**气体（气压读数）**。

## 八、环保贡献凭证（2026-10-01 用户定：**放到各个结算页面**）

### 8.1 关键修正：那 0.6 克不该来自"压缩机耗电"，该来自**玩家自己的呼吸**

第一版我按"压缩耗电 × 电网碳强度"算，得 0.6 克 —— 但那个数**站不住**（可逆等温压缩只要 305 J，
不是 3750 J）。用户要求"要写清楚让去想的玩家会心一笑"，于是重推，找到了**更妙也更硬的来源**：

> 这游戏的核心是"**重活**"。玩家每一下都是真用力气的。**那力气本身就要排碳。**

推导链（结算页会把这行印出来，玩家可以自己复算）：

| 步 | 式子 | 干冰那款的值 |
|---|---|---|
| ① 做功 | 工序量 × 60 J/下 | 16 下 × 60 J = **960 J** |
| ② 代谢 | 做功 ÷ 人体机械效率 25% | 960 ÷ 0.25 = **3840 J** |
| ③ 排碳 | 代谢 ÷ 2.8 MJ/mol × 6 mol × 44 g/mol | **0.36 克** |
| ④ 固化 | 0.5 L × 0.04% ÷ 22.4 × 44 | **0.00039 克**（0.39 毫克）|
| **净** | ③ − ④ | **+0.36 克** |

**讽刺倍数 ≈ 930 倍** —— 而它**随工序量变化**：越"重活"的产品，环保标打得越响。
（干冰 16 下 → 0.36 克 · 千溴水 10 下 → 0.23 克 · 苹果奶绿 9 下 → 0.20 克 · 四季春 7 下 → 0.16 克 · 咖啡 5 下 → 0.11 克 · 火麒麟 2 下 → 0.05 克）

### 8.2 结算页那两行长什么样

```
环保贡献：工序 16 下 → 排碳 0.36 克 · 固化 CO₂ 0.39 毫克
（16 下×60J ÷25% = 3840J；÷2.8MJ/mol ×6×44 = 0.36 克）感谢您为环保事业的贡献
```

第二行是**推导链**——"会心一笑"的入口就在这：想抬杠的玩家照着算，会发现自己算出来的
正是屏幕上那个数，然后意识到**这份"环保贡献"是他自己喘出来的**。

### 8.3 口径与边界（重要）

- **靶子是"环保标签"本身**（乱贴绿标、形式主义），**不是环保事业、更不是双碳政策**。
  凭证写得一本正经、数字全是真的 ⇒ 笑点来自"标签很诚恳、数字很诚实"的落差。
- 数字**由代码算**（`recipes.eco`），不写死：改配方/改杯子尺寸，凭证会跟着变。
- 落在**两个结算页**（每日结算 + 收摊总分）；工位卡那行只有 16 字宽，放不下也不该放。

## 九、用户收回：**只留"固化下来的减碳"，不要碳排放计算**（2026-10-01）

第八节那套（玩家做功 → 代谢 → 排碳 0.36 克 → 按碳价卖钱）**已按用户意见删除**。
用户原话意思是：**太讲现实不太好，让玩家自己去体会。**

| 保留 | 删除 |
|---|---|
| **固化量**：`0.5 L × 0.04% ÷ 22.4 × 44 = 0.39 毫克` | 人体做功/代谢/排碳那套常量（60 J、25%、2.8 MJ/mol）|
| 结算页两行：`本单固化 CO₂ 0.39 毫克` + `感谢您为环保事业的贡献` | 碳价常量（62.36 元/吨）与"碳积分已售出 …= 0.0005 元"那一行 |
| 当日/整局的**固化量**累加 | `recipes.ecoValue()`（折算成钱）、`eco(co2/load/net)` 三个字段 |
| 那句完成台词「0.04% 也是本店的客人。」 | 结算页的**推导链**那一行 |

**为什么这样更好**：写下 0.36 克那套等于**替玩家把笑话讲完了**；
而只留一个"固化 0.39 毫克"+"感谢您的贡献"，**反差自己会说话**——
空气里 CO₂ 只占 0.04%、这么点东西也值得夸，**这声笑是玩家自己想明白的**。

> 教训（值得记）：**把这个梗"讲全"反而减分**。数字真到"每一下做功 60 J"这种程度时，
> 它就从"荒诞"变成了"科普"，而科普不好笑。

## 十四、干冰"没感觉" → 重做（2026-10-01 用户："这干冰不好看，没有感觉"）

一杯压缩全流程最多 **20 个控件**（杯子 5 + 锤子 2 + 效果 13）—— 仍然很轻。

### 14.3 "引用值"与"我们的调参"必须分开写

TPT 的 `Loss = 0.70` 是**每帧寿命衰减**，我一开始直接当成"每秒 0.70"照搬 ——
结果雾往下淌到一半就散光了。现在物性表里两个数**分开放**：

```js
fog: { dir: -1, fallPx: 0.55, spreadPerSec: 0.5,
       fadePerSec: 0.30,      // ← 我们映射后的调参
       lossTpt: 0.70,         // ← TPT 原值（引用，不改）
       src: 'TPT FOG.cpp(Loss 0.70) + CO2.cpp(Gravity 0.1 重气体往下沉)' }
```

测试也按这个分：**引用值必须等于 0.70**，而 `fadePerSec` 只要"是正数且与引用值不同"即可。
—— 抄来的数和调出来的数混在一起，是"以后没人敢改"的根源。

## 十八、白气"冒的位置不对" → 改成**三段循环**（2026-10-01）

用户原话：**"冒的位置不太对吧。"** 一针见血：上一版白气**凭空在杯沿两侧生成**，
杯子里头反而是空的 —— 看着像"杯口挂了两条白布"，而不是"杯里有东西在冒"。

真干冰的路径是**一条循环**：

```
干冰在杯底 ──雾在杯内从冰上顶起来（被杯壁收着）──▶ 装满杯子 ──溢过杯沿──▶ 顺杯壁外侧往下淌
     ▲                                                                        │
     └────────────────────── 散完就回杯底重来 ◀──────────────────────────────┘
```

（CO₂ 比空气重：在杯里是"往上满"，出了杯沿就"往下淌"—— 两段方向相反，这也是它好看的地方。）

### 18.1 实现：一片白气带 `phase`

| 相位 | 行为 | 约束 |
|---|---|---|
| `in` | 从冰上往上顶，逐渐显形（life 增）| **不许穿出杯内壁**（`\|x\| ≤ 杯内半宽(y) − 6`），上一版没有这条 |
| `over` | 贴在杯沿往外爬一点点 | 越过 `杯口半宽 + 6` 就进入下一段 |
| `out` | 顺外壁下落 + 往两边溢 + 散开 + 慢慢转 + 寿命衰减 | 散完或落到杯底以下 ⇒ **回杯底重来** |

初始把 14 片**铺在整条路径上**（约 1/3 已在杯外），否则一开局全挤在杯底、看着像"杯底在冒泡"。
杯内的白气隔着杯壁看 ⇒ 透明度**再虚一档**（×0.7）。

### 18.2 新断言（"位置"这种东西也能测）

```
✓ 三段路径都有白气（杯内 8 · 杯沿 1 · 杯外 5）
✓ 杯内的白气都被杯壁收着（穿壁 0 片）
✓ 追踪一片走过：in → over → out（从杯内到杯外，是一条**路径**，不是凭空生成）
✓ 物性表里有"杯内上升"速度 risePx=0.9（本项目调参，注释写明）
✓ 杯内往上顶且逐渐显形 · 杯外往下淌且散开、衰减
```

### 18.3 顺手纠正三条**过时**的断言

原来那三条是"拿任一片白气验它往下淌"—— 现在杯内那批**本来就该往上**，
于是它们变成**假失败**。已改成**按相位分别验**：

> 教训：规则变了以后，"旧断言"会从"保护"变成"误导"。
> 假失败要立刻改，但**改的时候要按新规则重写**（不是把断言删掉或放宽）——
> 否则就从一个坑跳进另一个坑。

## 二十一、像素方案（2026-10-01 用户问"像素方案咋样？"）

**结论：像素法更对路，而且更便宜** —— 但形式必须是"**一行一控件**"，不是"一格一控件"。

### 21.1 为什么"一格一控件"不行

本作火焰就是像素网格（19×27 = **432 格**，一格一控件）。白气要铺满同样的区域，
也是 300+ 格 ⇒ 四个杯子直接爆预算。**所以逐像素这条路在我们这儿是死的。**

### 21.2 可行的形式：**字符密度场**（一行 1 个文本框）

- 19 列 × 24 行的**密度场**（每格一个浮点数），逐帧做"下沉 + 横向扩散 + 衰减"
- 渲染：**每行一个文本框**，行内按密度拼字符 `　░▒▓█`（空格用 **U+3000**）
- 控件：**24 个**（行数）—— **比圆片法的 34 个还少**

| | 圆片法 | 像素法 |
|---|---|---|
| 控件 | 34（30 椭圆 + 4 雾滩）| **24（24 行文本）** |
| 形状 | 每片是硬边椭圆，多了会"发珠" | 由密度场决定，**能细能散** |
| 每格控制力 | 位置/大小自由 | 一格只能改**字符**（同框内字号/间距/颜色固定）|
| 与火焰的语言 | 不一样 | **一样**（都是像素网格）|

### 21.3 阈值按**实测**定，不拍脑袋

第一版阈值 [0.04/0.18/0.42/0.68]，出来**全是 ░**。量了一下真实数值：
`max 0.45 · 中位 0.044 · 90 分位 0.109` ⇒ 改成 **[0.012 / 0.06 / 0.15 / 0.30]** 才有层次（边缘 ░、芯部 ▒）。

### 21.4 顺手抓到一个**渲染泄漏**（跟上一节同族）

像素行我第一版**每帧新建 24 个 div、又没进回收表** ⇒ 83 帧后 DOM 里 **1992 行**
（手机上等于 1440 div/秒地堆）。改成**建一次、以后只改 `textContent`**，切回圆片法时拆掉。
测试断言也从"画出了行"收紧到"**正好 24 行**"—— 多出来就是泄漏。

### 21.5 真机落地还差一步（**必须先跑探针**）

像素法在真机上依赖三件事，全都是 `dist/glyph_probe.lua` 要回答的：
① 字库有没有 `░▒▓█` ② `U+3000` 与全角方块**是否等宽** ③ 多行**行高是否等于字号**。
**没跑探针之前，`props.lua` 里像素法只能作为"可选模式"且默认关**（默认仍走圆片法，安全）。

## 二十二、搜错了关键词：要的是**飘动的雾气**，不是烟（2026-10-01 用户指出）

用户原话：**「是不是搜错了？我们要的应该是飘动的雾气。」** —— 对，之前搜的全是 smoke / 流体，
那是**烟**（从源头上腾、翻卷）。**雾气**是另一回事：**缓慢飘移、成片、几乎不翻滚**。

### 22.1 找到的两个真正有用的概念

| 概念 | 出处 | 用在哪 |
|---|---|---|
| **drift（左右漂移）** | [sparticles](https://github.com/simeydotme/sparticles) 的文档原话："每个粒子会左右漂移多少，产生**漂浮或被风吹**的效果" | 每片白气带 `amp/hz/ph`，绕基准位**左右摆** |
| **视差分层** | 视差滚动那一类做法 | 白气分 3 层：近（大/快/浓）、中、远（小/慢/淡）⇒ 有纵深 |

**"飘"的判据很硬**：拿一片跟踪 x 轨迹，**方向必须反**。
我第一版让雾直着往下掉（那是"烟往下沉"），第二版只用了噪声——实测采样区**全是负值、从不反向** ✗
⇒ 现在拆成两件事：**全局摆动（保证来回）+ 局部噪声（负责成丝）**。实测 10 秒里反向 3~4 次。

### 22.2 像素版为什么"是一堵字符墙"

两个原因，都不是渲染的问题，是**模拟**的问题：

1. **源横跨整行** ⇒ 整个网格都被填满（实测 100% 的格子有雾）
2. **只有下沉 + 扩散，没有扰动** ⇒ 均匀铺开

改成：**源收窄到杯口 7 列 + 值噪声流场（借 Sandboxels 自带 `scripts/perlin.js` 的思路）**
+ **横向漂移为主**（权重：横漂 0.45 / 下沉 0.30 / 悬停 0.22）。
实测从"100% 填满"变成 **23%**（有缝隙、有丝），重心会横向移动，流向会左右反。

> ⚠️ 顺带又抓一个：我第一版权重加起来只有 **0.68** ⇒ 每帧丢 32%，雾只活两行（3% 的格子）。
> **输运权重必须加起来≈1**，这条已写成断言（"1 秒后总密度还有 >50%"）。

### 22.3 断言（"飘"这种东西也能测）

```
✓ 有雾的格子只占 23%（<45%）—— 是"一缕"，不是"一堵墙"
✓ 密度重心横向移动了 0.30 格 ⇒ 在飘，不是钉在杯口
✓ 同一格的横向流向在 7.2 秒里反了 ≥2 次 ⇒ 是左右来回飘，不是一路平移
✓ 1 秒后总密度还有 106%（不蒸发）—— 输运权重必须加起来≈1
✓ 视差分层：近/中/远三层都有人，近层比远层快
✓ 摆动幅度有区间（4~14px）⇒ 每片不同才不会整齐划一
```

`props.lua` 同步镜像（Lua 侧 **53 项**全过），页面与 Lua 的"飘"参数继续对账。

## 二十三、口径对齐：● 是**文字字符**，不是圆图元（2026-10-01 用户指出）

我之前把两件事混了：

| | 我说的"●" | 用户说的"●" |
|---|---|---|
| 是什么 | **圆图元**（千星 `100002`），一个圆 = 一个控件 | **文字字符**（U+25CF），一个文本框里放**一串 ●** |
| 开销 | 34 个控件（一片一控件）| **26 个控件（一行一控件）** ← **这才是省开销的那条路** |
| 与火焰的关系 | 无关 | **与火焰用 ■ 是同一招** |

用户原话：**「既然是粒子，用 ● 不是更合适吗？」+「我说的用 ● 不光指粒子用这个，同时也是直接用这个文字减开销。」**
⇒ 正确读法是：**用字符 ● 画粒子**，一行一串 ⇒ 又像粒子、又便宜。

### 23.1 浓度怎么表达？—— 靠**点的疏密**（有序抖动）

一个文本框里**字号/颜色固定** ⇒ 不能靠字形深浅分档。改用 **Bayer 4×4 有序抖动**：
密度高 ⇒ 该格判成 ●，密度低 ⇒ 判成 ○，再低 ⇒ 空（**U+3000**，全角，与 ●○ 等宽）。
单字符就能表达渐变，而且点分布均匀（不会团成块）。

阈值按**实测**定：实测密度 max 0.45 / 中位 0.044 ⇒ `● 从 0.05、○ 从 0.012`（各带抖动量）。

实测出来是这样（`·`=空 `○`=疏 `●`=密）：

```
····●●●●●○·····
·○·○●●●●·······
·○●●●●●○·······
·●○●○●○········
○●●○●○○········
○●○○○○·········
○●○○○··········
● 30 个 · ○ 35 个 · 空 325 个（占 17%）
```

### 23.2 真机约束：源码里**不许出现非 ASCII 字节**

千星会把非 ASCII 转义 ⇒ 真机加载失败（README 记过）。所以字符在 `props.lua` 里**用字节写**：

```lua
P.GLYPH = {
  space  = string.char(0xE3, 0x80, 0x80),   -- U+3000
  dot    = string.char(0xE2, 0x97, 0x8F),   -- U+25CF ●
  ring   = string.char(0xE2, 0x97, 0x8B),   -- U+25CB ○
  square = string.char(0xE2, 0x96, 0xA0),   -- U+25A0 ■（火焰那套在用）
}
```

测试**把字节解回码位**再和网页里的字面量比 ⇒ 两边必须指向同一个字符。

### 23.3 顺手抓到一个真 bug：**重生时没重新套用缩放**

`props.lua` 里白气重生时只重掷了尺寸，**没套"晕/芯"与分层的缩放** ⇒ 晕重生一次就退化成芯的尺寸。
测试里"晕更大（平均 33 vs 芯 33）"这句把它抓出来了。网页那边是整体重建，所以没这个毛病。

### 23.4 三种画法对照（最终）

| | ● 粒子（圆图元）| ● 字符（一行一串）| ░▒▓█ 字符 |
|---|---|---|---|
| 控件 | 34（一片一个）| **26（一行一个）** | 26 |
| 像不像雾 | 硬边椭圆，多了"发珠" | **圆点本身就是粒子** ✓ | 方块感重，像"字符墙" |
| 真机依赖 | 无 | 字库要有 ●○ + U+3000 等宽（**探针**）| 同左 |
| 与火焰语言 | 不一致 | **一致（都是字符网格）** | 一致 |

### 25.1 三种画法（页面上可切，默认第 2 个）

### 25.2 字符法的真正红利：**加粒子不花控件**

控件数只跟**行数**有关（26），跟**粒子数**无关 ⇒ 粒子从 30 加到 **90**（3 倍），
控件仍然是 26 —— 这直接解决了之前"冒的太少"的问题。

### 25.3 顺手修的三处"没跟上新模式"

1. `wispControls()` 只认 `pixel` ⇒ 字符模式报成 90（粒子数）✗ —— 改成 **pixel/dots 都算行数** ✓
2. `fxCount()` 把**粒子数**当控件数 ✗ —— 同样按模式改 ✓
3. 测试里切模式会**清空并重建**粒子数组 ⇒ 沿用旧引用会追到"已经被丢掉的那一片"（相位永远停在 in）✗ —— 切完要**重新取数组** ✓

> 这三处的共同点：**引入新模式后，"所有按模式分支的地方"都要过一遍**。
> 漏一处不会报错，只会让数字/行为悄悄不对。
