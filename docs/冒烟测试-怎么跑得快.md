# 网页冒烟测试（`tests/smoke.mjs`）—— 怎么跑得快

> 为什么写这份：PC 上这套自检"几秒出结果"，但**同一套东西在这台 Android 手机上慢一个数量级**
> （实测：默认跑法光跑完各段单测、还没进主循环就 **超过 3 分钟**）。
> 这份文档先解释"慢在哪"，再给可直接用的旋钮，最后给"一劳永逸"的改法与风险。

---

## 一、先看时间模型（不看清就会白调参数）

这套自检是**用假 DOM 逐 tick 模拟整局**，所以：

```
耗时 ≈ tick 数 × 每 tick 成本
```

而 `DT = 1/30` 是写死的 ⇒ tick 数完全由"游戏内跑多少秒"决定：

| 段 | tick 数（≈） |
|---|---|
| 第 1 天（fast 模式 120 秒/天） | 3 600 |
| 各段定向单测（自动流转 12s + 排队耐心采样 + 到店采样…） | 约 1 000～2 000 |
| 默认停机点（进入第 2 天） | 上面两者之和 |
| `--full`（5 天） | 5 × 120 × 30 = 18 000 |

**结论**：只有三条路能变快 —— ① 少跑天数/秒数；② 跳过单测段；③ 加大 DT（但有代价，见四）。

## 二、现在就能用的旋钮

| 命令 | 效果 | 什么时候用 |
|---|---|---|
| `node tests/smoke.mjs` | 默认：fast 模式 + 跑到"进入第 2 天" | 一版改完的常规验证 |
| `node tests/smoke.mjs --html=雪皇的后厨-改良.html` | 测**改良副本**（默认测原版） | 网页改良迭代 |
| `--auto` | 只走"全自动流转"路径（机器人不拖票） | 想少分支、稳定复现某条路 |
| `--full` | 跑满 5 天 | **只有交付前才值得等**，平时别用 |
| `quick` / `fast` / `slow` | 5 / 10 / 20 分钟局 | `quick` 最快；`slow` 只会更慢 |

⚠️ **刚修掉的一个隐坑**：脚本原来写的是
`K.start(process.argv[2] === 'slow' ? 'slow' : 'fast')` ⇒ **传 `quick` 会被静默忽略**，
"我明明用了快模式"其实一直在跑 fast。现在三个都认了。
（教训同"参数被吞"那一类：**参数不生效时不会报错，只会让你以为调过了**。）

---

## 三、快速档旋钮（`--skip-units` / `--seconds=N` 已落地，`--dt=` 未加）

| 旋钮 | 实现要点 | 省多少 |
|---|---|---|
| `--seconds=N` | 主循环里比较游戏内 `elapsed`，超过 N 秒就收工 | 只想验"前 30 秒"⇒ 900 tick，是默认的 1/4 左右 |
| `--skip-units` | 把几段固定帧数的定向单测整段跳过，只跑主循环 | 直接砍掉那几百次采样（手机上这是大头） |
| `--dt=1/15` | 把 `DT` 从 1/30 改 1/15 | tick 减半；⚠️**数值会变**，只能当"跑不跑得起来"的粗筛 |

> 加 `--seconds` / `--skip-units` 是**纯跑法变化**，断言与结论不变；
> 加 `--dt` 是**改仿真精度**，断言可能因此变化 —— 两者要分清，别混着用来下结论。

---

## 四、真正的一劳永逸：假 DOM 每 tick 重建队列

代码注释里自己写了这条：

> 机器人显式拖票 + 点按钮（只为造出"在制+排队"的局面；原来跑 900 帧纯属浪费，**我的假 DOM 每帧重建队列**）

也就是说，主循环里每 tick 都在重建队列相关 DOM 节点 —— 这是成本的主体。
把队列元素**缓存起来、只在订单/小票变化时重建**，主循环成本可能降一个量级。

⚠️ 但这是**改测试骨架**，不是改跑法：
- 改完必须**与原版对跑一次**，比对：断言条数、出餐数、在制峰值、僵尸票帧数；
- 任何一个数字变了，先问"是骨架改错了，还是它抓到了真问题"——**不许为了让测试变绿而改骨架**。

## 五、推荐节奏（别每次都全量）

| 你在改什么 | 跑什么 | 期望耗时 |
|---|---|---|
| 画面 / 文案（CSS、HTML 结构不变） | 手机浏览器**直接刷新看** | 秒级 |
| 玩法逻辑（想快速知道有没有崩） | `--skip-units --seconds=30` | 秒级 |
| 一版改完 | 默认（fast + 停第 2 天） | 分钟级 |
| 交付 / 提交前 | `--full`，而且**放到 PC 上跑** | 只有这时值得等 |

## 六、顺带：这台设备上跑命令的通用提速规矩

很多"慢"不是设备慢，是命令写法的问题（`/storage` 走 FUSE、手机单核）：

1. **别扫 `/storage`**：`find /storage/emulated/0 …`、对大目录 `du -sh` 都是 FUSE 遍历，几千个文件就是几十秒。
2. **搜索限定目录 + `--include`**，并排除 `third_party/`、`_scratch/`、`node_modules/`。
3. **长命令一律后台跑 + 重定向到文件**，最后只 `tail` 几行；别让几十万行输出走管道（生成输出本身就贵）。
4. **循环里别反复起 `node -e`**：每次冷启动约 0.3～1 秒，10 次就是好几秒；能合成一个脚本就合成。
5. **一次调用做多件事**（`;` / `&&` 串起来），比来回多次调用省得多。
6. 能 `node` 就别 `python3 -c`（本机 Python 冷启动更贵），能 `grep` 就别写脚本。

## 七、实测与现状（2026-10-01 已落地）

### 7.1 已实现的两个旋钮

| 旋钮 | 语义 | 备注 |
|---|---|---|
| `--skip-units` | 跳过 5 段定向单测（连开4单上限 / 排队耐心 / 杯数→耐心 / 到店时间 / 自动流转反例），只跑主循环 | **纯跑法变化**，仿真精度不变 |
| `--seconds=N` | 主循环**再跑 N 秒游戏时间**就收工（从主跑开始那一刻起算，不是从开局） | 纯跑法变化 |

两者**都会在开头和结尾大声播报**跳过了什么、上限多少，并打印一行
`【本次档位】… ⇒ 这不是全量结果，交付前请跑默认档/--full`，防止把快跑当成全量结果。

### 7.2 秒级档会"不判"三条断言（这是设计，不是坏了）

`--seconds=N` 时，下列三条**必然无法成立**（20 秒不可能跨天/结算），已明确降级为
"打印一行 ℹ️ 不判"，而不是报红：

- 跑到第 2 天（跨过第 1 天结算）
- 至少出过一杯（闭环）
- 当日结算页弹出

想看这三条就加时间或去掉 `--seconds`。

### 7.3 实测数字（同一台 Android 设备）

| 档位 | 命令 | 耗时 | 结果 |
|---|---|---|---|
| **秒级** | `node tests/smoke.mjs --skip-units --seconds=20 --html=雪皇的后厨-改良.html` | **约 4.5 秒** | 全部通过 ✓（不含被跳过的 5 段单测） |
| 常规 | `node tests/smoke.mjs` | **分钟级**（>3 分钟；PC 上"几秒"） | 全量断言 |

⇒ 日常改逻辑用秒级档，交付前用常规档/--full，而且 `--full` 建议放 PC 上跑。

### 7.4 还没做的两件事

1. `--dt=1/15`：**没加**——它会改变仿真精度（数值会变），属于"改口径"而不是"改跑法"，
   要用也得单独标出来，不能与 `--skip-units` 混着下结论。
2. 假 DOM 的"每 tick 重建队列"仍未优化（见第四节）；那是数量级收益，但属改测试骨架，需与原版对跑比对数字。
